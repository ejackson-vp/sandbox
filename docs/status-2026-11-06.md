# Status report — 6 November 2026

Full status after Milestone 4 (capacity-aware admission and scheduling).
This supersedes the earlier short status note.

## Executive summary

x402 is a working, locally measured paid sandbox service with:

- accountless x402 payment and capability-scoped sessions,
- encrypted exec/files/services/HTTP/SSE/WebSocket operations,
- cold and warm-pool provisioning,
- suspend/resume with a filesystem checkpoint,
- baseline/peak resource specifications,
- capacity-aware admission with durable reservations,
- least-allocated multi-node placement,
- a tested, benchmarked local control plane.

It is still a **prototype substrate**:

- no KVM, Kata, Firecracker or TEE; kind Pods are not secure isolation,
- mock payments only,
- one controller, SQLite, local-path storage,
- filesystem checkpoints, not memory snapshots,
- no autoscaler, HA controller or production operations.

The product semantics and code structure are strong. The remaining gap is the
substrate and production operations, not the API shape.

## Milestone 4: capacity-aware admission

### Pure model

`controller/src/capacity/{types,placement,admission}.ts`:

- integer millicores, bytes and epoch milliseconds,
- node allocatable, platform overhead, labels, taints, readiness,
- baseline vs peak accounting (`CAPACITY_ACCOUNTING=baseline|peak`),
- storage retained while suspended,
- least-allocated placement with deterministic tie-break,
- no network, clock, Kubernetes or SQLite access.

Default is `baseline`: it reserves the Kubernetes scheduler request and leaves
limits as burst ceilings. `peak` reserves limits and rejects workloads that
baseline would overcommit.

### Durable reservations

`capacity/reservation-store.ts` is the port. `capacity/reservations.ts` is the
SQLite adapter.

States:

```
HELD → ALLOCATED → SUSPENDED → ALLOCATED
  │        │            │
  └expire  └terminate───┴→ RELEASING → RELEASED
```

Admission and insert happen in one `BEGIN IMMEDIATE` transaction. Unique
payment/session keys provide idempotency. `RELEASING` capacity is not returned
until the Pod is observed gone. Holds expire, and housekeeping repairs
terminal/suspended drift.

### Payment protocol

```
POST /v1/sessions (no payment)
  └─ capacity preflight → 402 or 503

POST /v1/sessions (payment)
  ├─ validate payment/spec/payer
  ├─ hold capacity before settlement ──► reject: 503, no charge
  ├─ claim intent
  ├─ verify
  ├─ settle
  └─ completeIntent
       └─ atomically attach hold to session
```

A capacity rejection is `503 capacity_unavailable` with `retryable` and the
requested vector. No node names, other sessions or cluster topology are exposed.

### Scheduling

Kubernetes remains the real scheduler. The controller chooses a node, sets
required node affinity for cold Pods, and reconciles reservation node with the
Pod's actual node. It is capacity planning plus placement intent, not a
replacement scheduler.

### Suspend/resume and warm pool

- Suspended sessions release compute and retain storage.
- Resume reacquires compute on the checkpoint node; failure leaves the session
  `SUSPENDED` and preserves the workspace.
- Warm Pods are counted from Kubernetes actuals; warm claims repin the reservation
  to the warm Pod's node.
- The warm pool remains optional and frozen; it is not an autoscaler.

50-create burst, pool 8:

| Policy | READY p50 | READY p95 | Warm hits |
|---|---:|---:|---:|
| unlimited | 16.07 s | 23.51 s | 8 |
| cap 4 | **10.37 s** | 27.54 s | 28 |

Cap 4 improves the median by letting the pool refill, but worsens the tail.

### Multi-node

Two-worker placement: 4 sessions split 2/2 across both workers, 1000m / 512 MiB
reserved per worker.

Two-worker burst with a **2500 MiB logical cap per node** (shared 7.75 GiB
Docker VM):

| Burst | 1 worker p50 / p95 | 2 workers p50 / p95 | 2-worker throughput |
|---:|---:|---:|---:|
| 10 | 755 ms / 2.24 s | 1.04 s / 2.88 s | 3.5/s |
| 25 | 3.18 s / 6.23 s | **3.08 s / 4.27 s** | **5.9/s** |

At 25 creates, tail latency and throughput improve; p50 is unchanged. This is
directional, not clean scaling: both workers share one VM's CPU and disk.

## Correctness evidence

- Ten competing admissions for one reservation produced exactly one winner.
- An eight-process, eight-connection SQLite test produced one winner.
- Holds survive controller restart; TTL expiry releases them.
- `RELEASING` capacity stays reserved while the Pod exists and releases after
  the Pod is gone.
- Suspend → B takes compute → A resume is rejected; A stays `SUSPENDED` with its
  workspace; B destroy → A resumes.
- Payment settlement cannot create a session without capacity in the normal
  path; the exception is a documented, retryable paid-but-capacity-lost state.
- Security suite on kind: 12 passed, 3 skipped (included in the 152).

## Comparisons

### FES

- **FES wins:** Firecracker/KVM isolation, warm-VM density, autoscaler, P2C
  placement, Redis pool state, production DaemonSet ops.
- **x402 wins:** payment-native admission, control-plane secrecy, lifecycle
  checkpoint/resume, richer data plane, egress policy, module discipline.
- Different products: FES executes short Python functions; x402 sells long-lived
  sandbox sessions.

### AWS Lambda MicroVMs

- AWS validates the lifecycle: snapshot-first launch, suspend/resume, idle
  policy, 8-hour cap, lifecycle hooks, port-scoped JWE endpoint, connectors.
- x402 matches the lifecycle vocabulary, idle policy, 8-hour cap, baseline/burst
  and per-session state.
- AWS still leads on memory snapshots, real Firecracker isolation, capacity
  quotas, managed ops and snapshot storage economics.
- x402 can beat AWS on payment-native admission, sealed-envelope secrecy,
  per-session egress policy, operation-level metering and runtime portability.

## Known gaps and risks

1. **No hardware isolation locally.** Kind Pods only; simulated attestation.
2. **Filesystem checkpoint, not memory snapshot.** Processes, sockets and
   in-memory state are lost on suspend.
3. **Node-pinned local-path storage.** Checkpoints cannot survive node loss;
   plaintext at rest unless the StorageClass encrypts.
4. **Single controller/SQLite.** The reservation port exists, but there is no
   shared conditional-write adapter, leader election or shared snapshot.
5. **Warm-pool transactionality.** Actual Pods are counted and claims repin,
   but there is no durable warm reservation transferred atomically.
6. **No capacity wait queue.** Deliberately omitted: the constrained burst
   occupies capacity until sessions end, so waiting cannot create capacity.
7. **Multi-node result is directional.** Shared Docker VM; not clean scaling.
8. **Fault injection is incomplete.** No live controller kill between hold and
   settlement, persistent Pod-deletion failure, or node loss during a pending
   reservation.
9. **Benchmark gaps.** No direct controller CPU/memory, queue-wait distribution,
   or 100-create run.
10. **Mock payments only.** No mainnet or production facilitator guarantees.

## Next steps

Ordered by observed limitation:

1. **Warm-pool transactionality** — durable warm reservation transferred to the
   session atomically; removes the last local correctness approximation.
2. **Shared conditional-write reservation adapter** — make the multi-controller
   story real rather than a port.
3. **Live fault injection** — controller crash between hold and settlement,
   persistent Pod-deletion failure, node loss while pending.
4. **Clean multi-node scaling** — separate VMs or real nodes; the current rig
   cannot answer additive-capacity questions.
5. **KVM snapshot experiment** — compare Firecracker restore against the 1.5–1.9 s
   resume and 1.8 s cold start.
