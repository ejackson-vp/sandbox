# Status note — 6 November 2026

One-page summary of where x402 is, what changed recently, and what is still
missing. Measurements are from the local kind rig unless stated otherwise; none
of them are memory-snapshot or TEE numbers.

## Where we are

x402 is a working, locally measured **paid sandbox service**:

- x402 payment handshake → capability → encrypted session
- cold and warm-pool provisioning
- encrypted exec, filesystem, services, HTTP, SSE and WebSocket data plane
- suspend/resume with a filesystem checkpoint
- idle policy, max lifetime, node affinity, fault recovery
- admission control, baseline/peak resources and a measured benchmark suite

It is still a **prototype substrate**: no `/dev/kvm`, no real TEE/Kata, mock
facilitator, one controller, SQLite and local-path storage.

## What works now

| Area | State |
|---|---|
| Payments | x402 v2 verify/settle in mock mode, replay-safe payment intents, capability derived from the settled payment |
| Session lifecycle | `PAID → PROVISIONING → READY ⇄ ACTIVE`, `SUSPENDING → SUSPENDED → RESUMING`, `TERMINATING → terminal` |
| Warm pool | Fixed-size, claim-once, no reuse; **off by default** (`WARM_POOL_SIZE=0`) |
| Cold start | Pod + guest ready path, measured at 1.80 s p50 locally |
| Warm start | 100.7 ms p50 with pool=8, paced at 1 req/s |
| Suspend/resume | Filesystem checkpoint on a per-session PVC; fresh guest keypair on resume |
| Data plane | exec/files, service processes, HTTP, SSE/chunked, polled WebSocket over the relay |
| Security model | sealed envelopes, hashed capabilities, relay-only ingress, egress proxy, non-dumpable guest |
| Fault handling | relay/controller restarts, PVC loss, node cordon, warm-pod kill |
| CLI/SDK | lifecycle, baseline, services, HTTP/SSE helpers; stable `SandboxClient` facade |
| Tests | 128 passed, 3 skipped in the latest full run |

Not claimed: confidential isolation, memory snapshots, TEE attestation,
multi-node scheduling, autoscaling, production HA, mainnet payments.

and runs in CI.

### Explicit suspend/resume states

The lifecycle now exposes `SUSPENDING` and `RESUMING`:

```text
READY/ACTIVE → SUSPENDING → SUSPENDED → RESUMING → READY
```

- `SUSPENDING` is atomic from a usable state and completed idempotently after a
  controller crash.
- `SUSPENDED` is only reachable from `SUSPENDING`.
- `RESUMING` handles the pod restore/readiness path, then `READY`.
- Resume timeout is measured from the resume start, not the original payment.
  This fixed a latent bug where a session suspended for more than
  `PROVISIONING_TIMEOUT_MS` could fail immediately on resume.

### Snapshot port

`controller/src/snapshotter.ts` defines:

```ts
Snapshotter.capture(session)
Snapshotter.restore(session)
Snapshotter.discard(session)
```

The local adapter is a **no-op** because the PVC is the checkpoint. It is wired
into suspend, resume and termination; the integration suite asserts the calls.
A future Firecracker/Kata adapter can implement memory snapshots behind the same
seam.

### Warm pool decision

The warm pool is a **development stand-in for snapshot restore**, not a scaling
strategy. It is already deliberately simpler than FES: fixed size, claim-once,
no reuse, no autoscaler, no Redis pool state. It stays off by default and should
be deleted when per-session Firecracker snapshot restore lands. See
[aws-microvms-comparison.md](aws-microvms-comparison.md).

restore replaces the pool.

## Comparisons

### FES

- **FES wins:** Firecracker/KVM hardware isolation, warm-VM reuse density,
  autoscaler, P2C placement, Redis pool state, production DaemonSet and ops.
- **x402 wins:** payment-native admission, control-plane secrecy, lifecycle
  checkpoint/resume, richer data plane, egress policy, and now module
  discipline. FES still has 1,211- and 942-line files; x402's largest module is
  564 lines.
- FES is an execution substrate for short Python functions. x402 is a paid,
  suspendable sandbox product. No overall winner.

### AWS Lambda MicroVMs

- AWS validates the lifecycle model: snapshot-first launch, suspend/resume,
  idle policy, 8-hour cap, lifecycle hooks, port-scoped JWE endpoint,
  network connectors.
- **x402 already matches:** lifecycle vocabulary, idle policy shape, 8-hour
  wall clock, baseline + burst, per-session state, no customer identity before
  payment.
- **AWS still ahead:** real memory snapshots, Firecracker isolation, capacity
  quotas, managed ops and snapshot storage economics.
- **x402 can beat AWS on:** payment-native admission, sealed-envelope
  control-plane secrecy, per-session egress policy, operation-level metering,
  runtime portability and relay-only ingress.
- **Do not copy:** JWE/IAM wire contract, warm-VM reuse across tenants, shared
  snapshot uniqueness, privileged controller, direct ingress as default.

## Known gaps and risks

1. **No hardware isolation locally.** Pod isolation only; simulated attestation
   is dev mode. Moving to cloud is not enough — it needs Firecracker/Kata/CoCo
   and `/dev/kvm`.
2. **Filesystem checkpoint, not memory snapshot.** Processes, sockets and
   in-memory state are gone on suspend. Services/streams/WebSockets stop.
3. **Node-pinned storage.** Local-path PVCs cannot move; node loss means
   `resume_unavailable`. No encrypted-at-rest guarantee.
4. **Single controller, SQLite.** No HA, no multi-node scheduling, no
   capacity-aware admission, no autoscaler.
5. **No snapshot storage accounting.** Suspend/resume is free in the mock
   payment model; production pricing is undecided.
6. **Mock payments only.** Testnet support exists in the payment layer, but no
   mainnet or real facilitator validation is claimed.
7. **Benchmark staleness.** Latest lifecycle-state change is covered by tests
   but not by a fresh performance run.

## Next steps

Recommended order:

1. **Capacity-aware admission.** Pure `admitCapacity(snapshot, request)`
   function, property-tested, checked before provisioning. This is local,
   useful, and does not need KVM.
2. **Lifecycle hooks.** Make `/run`, `/resume`, `/suspend`, `/terminate`
   explicit guest contracts, without copying AWS's HTTP wire format.
3. **Firecracker/Kata snapshot experiment.** One VM on a KVM host; measure
   boot, restore, exec, suspend and resume against the numbers above. Implement
   `Snapshotter` behind the existing port.
4. **Production ops.** HA store, multi-node controller, autoscaler, snapshot
   storage GC and pricing.
5. **Delete the warm pool** when snapshot restore is the primary fast path.
